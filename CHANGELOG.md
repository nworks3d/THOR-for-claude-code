# Changelog

What changed in each release, newest first. The release workflow copies the section for the tag being released to the top of the release notes and refuses to publish without one.

## Unreleased

- **A `requires` answer written without a hyphen is also met by a hyphenated spelling.** A rule that asked for "subagent" refused a brief that said "sub-agents". A hyphen between two letters no longer hides a plain answer; an answer that contains a hyphen itself, and every flag, is still matched literally.
- **`$p = Start-Process cmd.exe ...` is seen as a `Start-Process`.** The console-flash rule missed a command that follows a PowerShell assignment (`$p = ...`, `$p=...`, `$env:X += ...`). An assignment of a string, variable, number or group still runs nothing.
- **A short Windows switch such as `/it` no longer matches inside a path.** The scheduled-task rule refused `schtasks /create ... /tr C:/it/run.vbs`. A literal of a slash and one or two letters now matches only where a word starts.
- **A counted brace glued to a PowerShell word stays in the word.** `grep -P \x{2014}` was cut at the brace into three statements, so a trigger or an answer written with the braces never matched. Blocks and script blocks are still split.
- **A `requires` answer can be `<absolute-path>`.** Any real absolute path in the call (drive, UNC or Unix with two or more parts) satisfies it, so a rule can ask a call to name its folder without naming one folder. The trial writes a sample path, and the rule's text does not have to spell the token. Documented in `AGENTS.md`.
- **A rule that can refuse now outranks a note that only informs at the same severity.** At the command `Agent` five notes applied and the rule with a refusing check dropped out of the block of four behind an informing note, on id order alone. Severity is still the first key; the refusing rule wins the tie after it.
- **The session-start block has more room and its cut is exact.** The budget is 9,800 bytes (was 9,500; Claude Code shows a hook output whole up to 10,000 characters), and the room kept for the "N more standing rule(s) did not fit" line is that line's real size instead of a flat 220 bytes, so a full block no longer loses a rule to the guess. The line is printed whenever anything is cut.
- **A rule bound only to push or deploy now gets a note when it is written.** Those moments are usually reached only inside helper agents, so the session that writes the briefs may never see the rule. The write reply says to pin it or bind it to the tool the session calls; nothing is refused.
- **A THOR program that was removed (an antivirus quarantine) is now named, with the steps to get it back.** `doctor` and every session start check that the program each THOR hook, the tool-server entry, the memory's ship and backup sidecars and (in `doctor`) each scheduled task call is on disk, and say in one line what is missing, the likely cause and the Windows Security steps. On Windows `doctor` also names the THOR files Defender's own history shows, when readable without administrator rights. Only then may the assistant OFFER a Defender exclusion for the THOR program folder, after saying what it does, its risk and that one administrator prompt shows; it runs only after a clear yes (assistant rule in the first-session text, `docs/WHAT-THOR-DOES.md` E14, README troubleshooting).
- **The ship line no longer blames a sleeping machine.** It distinguishes never recorded (a task calls the ship but nothing was ever written), ran and failed (with the error) and program missing. The new example script `thor2/deploy/ship-hourly.example.ps1` records every failure, a missing program included, so the hourly task no longer dies silently.
- **Release step: submit each release's Windows binaries to Microsoft as a false positive** (CONTRIBUTING.md, Releases).
- **`install --set-helpers on` also pins the brief note.** `an-agent-brief-stands-alone` gets an always binding next to its Agent one, so it reaches the session before the first Agent call.
- **A helper's numbers are passed on as "according to the helper's report".** One sentence added to the reminder of the `absolute-verification-claim` reply rule.

- **A second machine can run the full hooks on a read-only copy of the memory.** A store with a `thor-copy.json` marker beside it (or `THOR_COPY=1`) is a copy: every hook arm opens it read-only and never appends an event, so the single-writer log cannot fork. What the hooks would have logged (served items, refusals) goes to `copy-telemetry.jsonl` beside the copy; the once-per-context showing keeps working; the weekly check is not asked there (session start says so in one line) and the stop holds that only a log write can settle (setup, decisions to capture, crowded places, stale rules) are off. `sync pull` refreshes the copy from the backup git clone, atomically, and keeps the old copy when it fails.
- **A project can have a working copy per machine (opt-in).** `install --register-root --per-machine` registers a checkout for this machine only, `--ask-main` prints the one command a copy-holding laptop runs on the main machine (`install --register-machine-root`), and every reader resolves the registration of the machine it runs on. A normal one-machine install is unchanged.
- **A refused file edit is no longer taken for a command in the bug detector.** Two rules that correctly refused edits of the same file were reported as a "false-block pattern" blaming the command matcher, because the file path was read as a command word. A refused call that is one path token (no whitespace, holding a path separator) now yields no command word and is never grouped; real command-word patterns still count.

## 2.5.0 (2026-10-02)

- **The first reply of a new install is no longer held for being long, and the first-session list is clearer.** The reply MUST show the twelve-item list (about 2,900 characters) and the user did not ask for an overview, so the length rule would have held the very first reply. A reply that is that list (numbered lines 1 to 10 or more, the `/thor-eval` command and `CHANGELOG.md` kept verbatim, so it works in any language, at most 6,000 characters) is now exempt from the rules about how a reply reads; the honesty rules still read it, and a plain long reply later is still held. Item 1 now says that Pro and any plan below Max count as small (`install --set-plan small`), Max as max, and that a plan the settings do not name is small until the user says otherwise. The assistant rules say how to switch the connections of item 2 back on (run `install --db <store>` again: it wires the four entries, a second run changes nothing, restart Claude Code), and items 4 and 7 say they only happen while those connections are on.
- **The first-session lookup is enough on its own.** A blind test of a new user's assistant, with only what THOR serves, had to guess the two setup calls, where the installer lives and which settings file to edit, because those lived only in `AGENTS.md`, which the user's own project does not hold. `first-session-questions` now carries, in its assistant part, what to say first, the exact `remember` and `retract` calls, a PATHS section with the real installer, store, settings file and tool-server file of this install (written when `install` seeds the memory), the three facts (lanes, project names, correcting the memory) and what to do with a fact whose anchor is unknown (store it pinned, offer once to attach the hostname). They are one catalogue rendered into the lookup and into `AGENTS.md`, which no longer repeats them by hand. Item 12 is now a statement ("I create CHANGELOG.md; say no and I do not") instead of a question, and saying no to item 2 removes only THOR's four hook entries from the settings file: the `thor` tool server stays, so notes can still be searched and saved, and the change takes effect after a restart. The setup note and the turn-end reminder now point at `lookup first-session-questions` as the one place to read.
- **A second install no longer overwrites the backup of your settings.** `settings.json.bak` was rewritten on every run, so after a second `install` (or `install --set-backup`) it held the file THOR had already wired, not your original, which the "Remove THOR completely" steps rely on. A `.bak` is now written only when none exists yet, for `settings.json` and `.claude.json` alike, including the copy made by `install --set-backup off`.
- **A reply that claims everything was checked, without saying what it covered, is held.** New seeded reply rule `absolute-verification-claim` ("alles nagekeken", "alles klopt", "everything checks out", ...): it fires even when the turn looked at something, and stays quiet when the reply names its scope ("niet nagekeken", "volgens de helper", "except ..."), negates the word, quotes it, or only promises to check later. The rulebook gets three optional fields for this: `hedge_words_before`, `scope_words_after` and `list_label_scopes`. A new memory now gets six reply rules; an existing rulebook is left as it is.
- **A rewritten rule is no longer hidden for verdicts on its old version, and a rule that can refuse is never hidden.** Decay hid a note after two noise marks since the last useful mark, even when the note had since been rewritten or had gained a check; one live rule that refused calls (17 real refusals) was never shown at the call it guards. Noise marks now count only since the last revision that changed the text, the check or the bindings, and a rule whose check can refuse (`forbidden`, `requires`, `contains`, `absent`, `absent_all`) is never retired from showing. A plain, unrevised note still decays after two noise marks, and a pinned note still never does.
- **Helper-agent mode is off in a new memory, and one command switches it on.** The two notes that carry it (`orchestrator-mode-saves-quota` and `an-agent-brief-stands-alone`) are no longer seeded, so the starter pack is 13 notes. `install --set-helpers on --db <store>` stores exactly those two, `install --set-helpers off --db <store>` retracts them with a reason, and either is safe to repeat. A retracted id cannot be created a second time, so `on` after an `off` stores the note again and resolves the id onto the new version. First-session item 6 now says "Default: off", keeps the 12 to 62 percent measurement, and lists the reasons you may not want it: you cannot see or steer the work, each helper starts with a fixed context cost, it knows nothing beyond its brief, parallel helpers can collide in the same files, and checking costs an extra turn. A memory that already has the notes keeps them.
- **The backup and the real-call record are the user's choice, and the first-session list is short.** A fresh install wired no backup, yet the list said a daily copy was on; it now says nothing is backed up until you choose. `install --set-backup local` makes a git folder beside the memory (no remote, nothing leaves the machine), `install --set-backup <folder or address>` also adds it as the remote `nas` (an empty or missing folder becomes the bare repository, and the branch is pushed once), and `install --set-backup off` removes only the session-start hook; each choice runs the backup once to prove it works and says so plainly. A backup repository with no remote at all now commits and never pushes. `install --set-recording off|on` stops (or resumes) the record of real calls and replies, and `serve sweep` then says it has no data instead of "none would refuse". The list has two new items (the record, and a changelog with a version number, default yes when the project has none) and shows the user only a two-line intro, one line per item and how to answer; the why and the way to say no per item stay in an appendix for the assistant, who states a why once, only when asked about a number or refused.
- **The first session shows a numbered list of everything the install arranged, and nothing waits for an answer.** Twelve items, each in plain words with what it is, why it exists (the measurement or the real reason, one sentence), what was chosen and how to say no: your plan, the connections to Claude Code, the git hooks, the weekly check, the starter work rules (listed from the pack itself), helper-agent mode, bug reporting, reply language and length, folders for a topic, backups, the record of real calls, and a changelog. The defaults are applied and recorded first, in the same turn; you then answer by number ("1 yes, 3 no, the rest as you like") and anything you do not mention keeps its default. On an answer that works against you the assistant says why the item exists once and then does what you decided. The list is one catalogue in the code, rendered into the memory as the lookup item `first-session-questions` (the setup note now just points at it) and into `AGENTS.md`, which a test holds equal. The weekly check and bug reporting can now really be switched off: `install --set-weekly-check off` and `install --set-mode off`, and a later install keeps both off.
- **The starter pack has 15 notes, and on Windows two of them refuse a console window flash.** `windowless-processes-on-windows` now refuses a `Start-Process` that is not hidden (it still lets through `-WindowStyle Normal` for a window you asked to see, a browser address, a control panel or a settings page), and the new `scheduled-task-not-interactive` refuses `schtasks /create` with `/it`. On other systems both are plain notes, and every other starter note still only informs. The changelog note no longer says it never creates a file: a changelog is created only when you said yes to first-session item 12. The docs were brought in line with the code: README and AGENTS.md match what the programs do, forbidden checks skip calls that do nothing (`--help`, `--dry-run`), the capture guard defaults are stated, backup is described as a first-session choice, and there is a new "Remove THOR completely" section in README.md and an overview of everything THOR does, `docs/WHAT-THOR-DOES.md`.
- **Step 1 of the evaluation skips tests that nothing has changed since.** `doctor --eval` prints a `test signal:` line for the project, read from the calls THOR records at each Stop: either "may skip" (the last test or build run passed, within 7 days, and no code was edited and no tree-rewriting git command ran after it) or "run the tests in step 1".
- **The two helper-agent notes now say what the usage measurement showed.** One helper per task and no bundles, targeted tests while working and one full run at the end, a check every 20 to 30 minutes at most three times and then judge the job dead by its last real activity and not its status, a summary instead of a read-first list, trivial tasks done directly. No model names.
- **A summary or overview you ask for may run longer than 1000 characters.** The length rule gets `overview_request_any_of` and `overview_max_chars` (2500): found when a requested summary of about 1,100 characters was held. A rulebook without the fields behaves as before.
- **The evaluation runs once a week per project, tied to your plan.** The 16-hour window and the three-hour re-ask are gone. THOR reads the plan from Claude Code's own settings at install (`organizationRateLimitTier`, undocumented, so it fails soft and you confirm it in the first-session questions) and keeps it in the mode sidecar with who said so. A smaller plan is strictly weekly. Max is weekly and daily while rot is found (a defect, a false-block sweep hit, an owed batch or dispute item, a report that did not count, a THOR bug candidate), and back to weekly once a counting evaluation finds none. The ask says which mode applies. `install --set-plan max|small` records your answer.
- **The evaluation ask names every report that did not count and the last one that did, and a repeated restart notice is said once.** Field tests of the evaluation routine showed an agent taking a dead report for a counted one, a signals window that restarted at a dead report so its refusals never reached a report that counts, 14 identical "does not count" lines in two hours, and an ask that always said "1 item owed a verdict" which no evaluation lists. The ask now lists each dead report with its reason and the last report that counts; a new evaluation's window starts at that report; a restart notice is said once per report and session; the ask counts the verdict list of the evaluation apart from items owed only because other sessions fired them; `doctor` names the machine-section renderer of each installed program and says whether filings count. A refusal for a full place now says plainly that a Report never fires.
- **Guard corrections from the same tests.** A `contains` check on text that only sits in comments or in a script's help text is a note, not a proven guard; the trial of a `requires` check also tries multi-statement PowerShell calls; `--help` exempts a call only where it comes first after the program or its subcommand; `USERPROFILE` set to the real profile is no sandbox; a remote rewritten with `url.insteadOf` is matched under both spellings; and `capture-owed.json` drops markers older than 30 days. In the answer guard a claim of checking is backed only by a look that shares a word with the claim, and a rule marked `quotes_exempt` ignores its phrase inside quotation marks.
- **THOR tries every rule against the calls and replies of the last 30 days by itself, and says which would refuse what ran fine.** The two one-off replays of 2026-10-09 (146,000 real calls, 6,600 real replies) found twelve rules with false blocks and 21 false answer-guard triggers that no review had shown; that check is now THOR's own. Every end of a turn keeps the turn's tool calls and the reply the answer guard judged in two bounded sidecars beside the store (`real-calls.jsonl`, `real-replies.jsonl`, 30 days, size-capped, redacted like the log). `serve sweep` replays every rule that can refuse, and every answer-rulebook entry, against them through the hook's own functions and prints, per rule, how many real calls it would refuse and how many of those ran fine, with examples; it is incremental and time-boxed, and `serve sweep --backfill` reads the last 30 days of transcripts on a machine that starts empty. `doctor` and `doctor --eval` print one line when a rule would refuse real calls that ran fine (silent at zero), the evaluation start note lists those rules as item d of section 2 with the call that settles each, and `remember` and `revise` of a rule that can refuse now say how many real calls of the last 30 days it would have refused, with up to three. The refusal-outcomes proxy points at the sweep, because it cannot see a false block that was walked around without weakening the rule.
- **THOR finds its own bugs and offers one per session to be written up.** Signals THOR already records - a report refused as version skew, a machine-section mismatch with the same format on both sides, a filing gate that disagrees with itself, a hook launch failure that was not the machine going to sleep, a panic inside a hook, several unrelated rules loosened after refusing the same kind of command, a start note that had to leave an item out, a refused starting note, a `doctor --eval` line the routine never names - become bug candidates with a stable fingerprint, kept in `thor-bug-candidates.json` beside the memory. The first prompt the owner types in a session carries at most one, as a nudge that holds nothing: an issue for the public THOR repository, drafted from THOR's evidence with paths, project names, hosts, addresses, user names, session ids and secrets replaced, to be opened only with the owner's yes. The outcome is recorded with `remember` as a Report `thor-bug-<fingerprint>` tagged `thor-bug:<fingerprint>`, which needs no project; no new tool. The mode comes from `install` and is `release` on every build, a source build included; only `install --set-mode test` makes `test`, where the agent only shows the write-up to the owner and pushes nothing. In `release` the agent asks the user ONE plain question, in the user's language, showing the exact English text that would be sent and saying what was taken out (file paths, project and folder names, computer and user names, addresses, keys and passwords), that nothing is sent without a yes and that no is fine; after a yes it runs `gh issue create`, or opens a prefilled new-issue address in the browser when `gh` is missing, so the user only clicks Submit. An install closes every older candidate as resolved by the upgrade and moves the scan past the old log: only new evidence from the running build can raise one. `install --set-mode release|test --db "<path to thor.db>"` changes it, and with no mode on record nothing is offered. `doctor` has a `THOR bug candidates:` line.
- **Zero-touch prerequisites, and orchestrator mode in the starter pack.** The agent route in `AGENTS.md` now checks for git (Git for Windows on Windows, which is also the Git Bash that runs Claude Code's hooks), Python 3 and the Visual C++ runtime, and installs what is missing with winget, brew, apt or dnf, with at most one permission prompt from the system. The starter pack has a new note, `orchestrator-mode-saves-quota`: the strongest model answers questions, judges and checks, cheaper models do the real work in helper agents, trivial tasks are done directly, and with no strongest model the best available one steers. The agent-brief note now also asks for known facts, one narrow task with a stop point and a short report, and folds in the parallel-agents point, so a new memory seeds 36 notes (22 and 14), plus the first-session list. The machine-section renderer is now 8 because the section can carry the false-block sweep line.
- **A new memory starts with a set of general work rules, and installing takes one sentence to your assistant.** A store the installer creates now also gets 14 notes tagged `workflow-starter`: a changelog line with every user-visible change (only when the project keeps a changelog), tests run and the real result quoted before "done", no secret in a commit, push and deploy only on your word, check where you push, a scan before anything goes public, a complete brief for every spawned agent, and a few more. They were picked from what was marked useful in the author's own memory and rewritten to hold on any project. Each one is bound to the commit, push, publish, delete, deploy, install, agent spawn or command it is about instead of being pinned, and none carries a check: seven candidate checks were replayed through the real guard over 145,976 recorded tool calls and every one either refused legitimate calls or had nothing to prove it on, so a new user cannot be blocked by a rule they did not write. An existing memory is never seeded.
- **The first session finishes on defaults, without asking.** The setup note and the turn-end reminder now carry the defaults themselves (short replies, the owner's language, work lane only, every starting note kept) and say to apply them without waiting, so a fresh agent that never read AGENTS.md completes the setup in one sentence. AGENTS.md opens with the whole install in five steps, built on the release download instead of a Rust build; the only thing asked of the person is one restart. `install.sh` and `install.ps1` accept `THOR_RELEASE_BASE` to fetch from another folder, `install.ps1` checks for the Visual C++ runtime before starting a program that would otherwise open a dialog nobody can click, and it stops with the real exit code when the setup fails instead of printing "Done".
- **A reply that says "checked" is no longer held when the turn really looked, and no rule asks for a file name any more.** Found by replaying 30 days of real replies through the answer guard (6700 turn ends). The rule `checked-claim-needs-evidence` held replies whose turn had run curl, git, a node check or a doctor run, and its reminder asked for a `path:line`, which the owner's own short-answer rule forbids in a reply to him. A rule marked `backed_by_turn_tools` now stands aside when the turn ran a command or read, searched, fetched or opened something; a claim relayed from an agent's report, or made in a turn that looked at nothing, is still held, and so is an unsupported claim in the assistant's own words next to a quote. The same rule now reads only the assistant's own, affirmative claims (`own_claims_only`, `affirmative_only`), so "Niet volledig gecheckt:" and a claim inside a message drafted for someone else are no claim, and it takes "according to the agent's report" and "earlier this session" as honest answers. `claim-no-access-without-checking` takes the same field. A new field, `only_if_prompt_any_of`, keeps "do not bounce his commit request back" to prompts that asked for a commit. `turn_commands` now also lists a `[tool] Name` marker for each other tool call that looks.
- **Calls that do nothing are no longer refused, and a few that were refused by mistake pass.** Found by replaying 30 days of real tool calls through the guard. A shell command anchor such as `grep` no longer reaches the Grep tool (nor the shell word `agent` the Agent tool); an `until` loop in a Monitor call is bounded by the tool's own timeout; `git push --dry-run` (or `-n`), PowerShell `-WhatIf` and any call carrying `--help` are not refused by a forbidden, requires or owner-approval rule; `git -C $b push` and `cd $b` read the variable an earlier command of the same call set, and a `git` command in a repository the call itself makes, or one of no project the memory knows, is not judged by the session's project; and `export USERPROFILE=...; install.exe` answers a requirement written `USERPROFILE=` like the inline form did. Every case has its harmful twin in `serve/tests/sweep_false_blocks.rs`. The write-time trial inside the memory server (`mcp.exe`) still reads the old rules until it is next installed.
- **`doctor --eval` is the fast health check for an evaluation, and the full one is much quicker too.** The evaluation routine asks for nine lines of the health check (`provable rules`, `gate`, `teeth`, `pinned`, `decay`, `crowding`, `ship`, `judgement debt`, `contradictions`), and the full check took 150 to 190 seconds on a large store, so an agent started it in the background, filed its report before it ended and wrote "not verified". `doctor --db "<path to thor.db>" --eval` prints only those lines, each exactly as the full check prints it (it calls the same functions, and a test holds the lines equal), plus a last line saying what it left out; it ends in about 7 seconds on a store of 270,000 events, and the routine now tells the agent to run it in the foreground and wait. The same work made the full check itself about 8 times faster (19 seconds) with the same output: the teeth line asked the log about one session at a time, a full pass over the log for each of hundreds of refusals (63 seconds), the refusal outcomes line did the same (55 seconds), and the crowding line parsed the same candidate pool and the same command once per probe (19 seconds). No store is changed and no index is added: the by-session reads are answered from one pass when a reader turns that on, and never from a log older than the one on disk. The allowed-tools entry for `doctor` already covers the new flag.

- **A dispute needs its reason, and the evaluation makes an agent verify each one.** `legitimate_calls`, `may_change` and `accept_refusing` now need `because` on `remember` and `revise`: one sentence of at least 20 characters saying why the span may change, or why the call is legitimate, while the rule stays true. Without it the write is refused, and the refusal says to try the better path first - hang a check on the literal that is the rule's subject, and dispute only an incidental span. The reason is kept in the item's history. The evaluation's machine section lists every dispute written in its window with the argument, the calls or spans and the reason ("no reason recorded" for an older one), and says when the agent verified it afterwards. The start note adds item c, DISPUTES TO VERIFY: every unanswered dispute written since the project's previous report (at most 8, the rest first next time), each with two exact calls - hang the real check, or confirm the dispute with a reason - and the report is held until each one is answered. `serve retest` no longer carries a dispute that has no reason on record: it tries the rule without it and says so. `doctor` prints the reason beside each dispute.
- **The evaluation starts from the previous report's remarks.** Before judging what fired, it looks up the newest evaluation report filed for this project and either settles what that report's remarks left open - unjudged items, gaps, anything still to be probed - now, or writes it down again with the reason it is still open. THOR's own open points are not part of this: THOR writes and closes those itself (see below).
- **A project worked in for an hour cannot end a turn without a recent evaluation report, only inside a project.** In every project that has had an hour of work since its last evaluation that counts, and where the session has put in at least ten minutes of its own work, the Stop hook blocks the FIRST Stop of EVERY turn - not merely once per session - until an evaluation report that counts is on file for that project, before the judgement debt, when both are due, and regardless of how many notes currently owe a verdict. A report that counts covers the next 16 hours: a rolling window rather than a calendar day, so a report filed late at night is not undone by the next midnight, and one filed early in the afternoon no longer buys silence clean through to the next morning. Each ask names how many times this project has already been asked and since when. A checkout that resolves to no project is never asked on its own, since there would be no way to ever file the report that silences it. The entries at the end of this section say what changed about who is asked.
- **Filing the evaluation report is refused while the log still shows the work undone.** The obligation used to lift the moment a report existed, and nobody read it, so a session could discharge a day's review with prose. Now the write gate checks the events instead of the text: every item on the evaluation's three frozen lists must be settled - each verdict given with THOR's own tool, each rule of the batch and of the A4 list decided by THOR's trial as it reads the rule now - and the refusal names what is missing, item by item, and sends the writer to the work itself, never to a pass that relabels in bulk. Moving a report that was filed for another project onto this one is a filing too, held to the same conditions. A rule the batch does not hold stays owed and leads the next evaluation.
- **Open points are THOR's own now, and the owner has a queue.** An open point is a small note THOR itself writes, one per blocker it finds (a project with no registered working copy, a checkout that is mid-change while the default branch still has the line a check needs), and closes itself, with a reason it derives, at the first evaluation start after the blocker is gone. A session can no longer file, tag or remove one: `remember`, `revise` and `retract` refuse it, the routine no longer asks for it, and a written reason settles nothing. An open point that is still there after an evaluation that counts was filed is in the owner's queue: its text says "the owner decides" and names which sessions carried it, and once a project has more than 8 of them every new session there opens with a line telling the owner how many wait, each one saying what to do, step by step. The queue never refuses anything, and `doctor` names every point, and the ones an agent filed by hand before this release, apart.
- **One evaluation settles a batch of rules, not the whole backlog, and THOR does the rest itself.** At the start of an evaluation THOR tries the project's old rules itself, in a time box of 20 seconds (`THOR_MACHINE_PASS_SECS` changes it, 1 to 200), and writes a rule, a note or one of its own open points for each. What it cannot decide alone goes to the agent: a batch of at most eight rules that need a fix only an agent can make, and an A4 list of at most sixteen whose check bites and whose text only has to name its literal, each with its reason and the exact call to make. Both lists are frozen when the evaluation starts, hold still while it works, and what they leave out stays owed and leads the next evaluation, which also starts with what this one did not reach. The ask names the lists, the refusal counts what is left, and `doctor` names both on the `evaluation batch` line.
- **An evaluation is held to the lists it started with, and only to what fired in its own session.** The filing gate used to compute the judgement debt live and store-wide at every attempt, so the evaluation's own writes (which fire every rule bound to the `remember` moment) and parallel sessions kept adding to it: measured in a fresh evaluation, eight attempts were refused on a list of 14, 6, 13, 4, 4, 1, 5 and 4 items, and the session ended up marking sixty items useful, some it never saw fire. The evaluation now starts in the memory's own log - when the routine is opened or when the Stop hook asks for it, never at a filing attempt - with a start record that freezes the judgement list (only what fired in the evaluating session, 40 times or more since its last verdict), the batch and the A4 list; the note that starts it names all three, and no file beside the store hands anything over any more. Items that fired only elsewhere stay owed store-wide and `doctor` keeps naming them. An item that cannot be judged honestly can be skipped with a tag `not-judgeable:<id>:<reason>` on the report, so "when in doubt, skip" no longer collides with a debt that must reach zero. A write to an item on the frozen lists from outside an attested THOR call of the evaluation voids it, and the next Stop starts a fresh one.
- **Every rule is tried the moment it is written, and the answer is one of three.** `remember`, `revise`, `pin` and `unpin` now run every rule and orientation, whatever its severity, through the same guard the hook uses, before anything is stored. The reply says which of three things happened. RULE (`teeth: wired, not proven`, or `teeth: proven guard` once a real refusal or the file's own git history backs it too): the check refused the call it forbids and let the ordinary calls through, so it is stored. NOTE (`teeth: note`): no tooth holds, so the rule is stored without a check; it still arrives at its moment, ranked by its severity as before, and can only inform. REFUSED: nothing is written, and the reply names the one fix. Besides the check the writer gives, THOR builds teeth from the rule's own words - a flag in a backtick span after the command the rule is bound to, a quoted call, a span that stands in a file the rule is anchored to - and when the writer gave no check that works, one of those that bites refuses the write, naming the exact check to hang ("Hang it: check_kind forbidden, check_literals ['--force']"). A tooth that a real call from another session in the log carries does not force, and the reply names that call. A check that would also refuse a listing or help call of its own command (`git tag -l`, `<command> --help`) is not stored. A `revise` that changes only tags, the falsifier, the expiry or the key keeps the verdict the rule had and runs no trial. The `teeth:` labels are written by this trial only: a writer cannot set one, and a program that changes a rule by hand drops its label, which leaves the rule undecided until it is tried again. This replaces the labels, the answers and the gate ground described in the entries above: `teeth:informing`, `teeth:refuses-legitimate-use` and `teeth:anchor-collapsed` are never written again (an old one stays readable and decides nothing), a `no-literal:` or `no-catch-on-command:` tag answers nothing and is no longer asked for, and `revise` no longer takes `trial_check` - a caller still sending it is told which fields the call takes.
- **A check's literal has to be named in the rule's own text.** A check whose literal the text never mentions is refused whenever the check is attached or changed: a tooth has to say in its own words what it refuses, so every serving shows it. A character outside plain ASCII is named by its code point - write `U+2014` in the text for an em dash - and when naming a long literal would take more than 120 of the 300 characters, the refusal proposes a shorter distinctive one. A rule that already carries such a check is never blocked by it on a pin, an unpin or an edit that leaves the check alone: the write lands, and the rule stays undecided, with the fix named, until its text names the literal.
- **An old `contains` check that really bites counts as a tooth, once, and shows what it guards.** The rule above holds for every new write and for every change to a check, of every kind. Rules written before it often keep a line of their own file with a `contains` check whose text never names that line, and the file proves the line is real, so `serve retest --apply` now counts such a check as a tooth when it stood on the rule, with its text and anchors, at a fixed cutoff, and it bites both ways in the working copy registered for the rule's project: removing the line is refused, keeping it is let through. The first such verdict records that cutoff once, as THOR's own record `teeth-a4-cutoff`, and it never moves. Every such rule shows the fragment it guards - which line, in which file - in its `retest` output, on its step in `history` and in `doctor` (`teeth old contains (Q24)`), so you can judge whether that line really guards what the rule is about: if it does, name it in the rule's text; if it does not, clear the check with a `because`. Only THOR's retest writes that mark; no argument sets or clears it. Any revise of the rule's check, text or anchors ends the exemption for good, and the name is asked for from then on. No other kind of check is exempt.
- **A command that already contains its own literal is a whole-command ban, and a real rule.** A rule bound to `sshpass` that forbids `sshpass` used to be labelled a collapsed anchor that claimed no tooth. It is now tried as a ban: the call itself must be refused, while a mention of it (`echo sshpass`) - and, for a command of two or more words, `<program> --version` - must go through. It is stored on the rule track, and when a narrower anchor would bite as well, the reply names it as advice.
- **Three new arguments answer a refusal that is right about the tooth but wrong about the rule.** `remember` and `revise` take them, and each is meant for one kind of refusal only. `legitimate_calls: ["git bundle list-heads backup.bundle"]` names a real call that a tooth THOR built from the text would refuse, and which is legitimate. `may_change: ["version"]` names a span of a file that a `contains` check THOR built would freeze, when that span is allowed to change. Either one stores the rule as a note by dispute: no check, the dispute kept in its record, and `doctor` listing it for the owner. `accept_refusing: ["git push origin main"]` is for the opposite case. A check that would refuse more than half of the real calls it reaches in the log (at least five of them) is refused as too broad, listing those calls: narrow it - a longer literal, a narrower anchor - or, when refusing them is exactly the point (a "never push this repository until the owner says so" ban), name one of the listed calls there. The rule then stays on the rule track, and `doctor` lists it with the calls it accepts refusing.
- **A file check waits for the project's own working copy instead of guessing one.** THOR tries a `contains`, `absent`, `absent_all` or `path_exists` check in the checkout registered for the rule's project (next entry), never in whatever folder the session happens to be in. Written from inside that project before it is registered, the rule is refused with the one command to run there. Written from anywhere else - the project is not on this machine, or the session works in another project - it is stored as a note that keeps the check pending: the check is kept in the note's record, never live, and the note claims no guard. So is a check that holds in the session's own checkout (a worktree, another branch) but not yet in the registered one, because hanging it now would refuse every edit of that file in the registered checkout. `doctor` lists every note with a pending check. Once the project is registered and the check holds in its registered checkout, `serve --db "<path to thor.db>" retest --id <id> --apply` tries it again and hangs it if it bites. A rule written before this release keeps a file check whose project has no registered working copy: it counts as blocked, not as undone, until the project is registered, and from then on it is asked about like any other undecided rule.
- **Run `install` once from inside each repository, so THOR knows its working copy.** The trial above needs the one folder on this machine that is each project's real checkout, and it never guesses that from the folder a session happens to be in. A new per-project install registers the checkout it runs in by itself; a project whose code an earlier release already read has no working copy registered yet. For each repository you use with THOR:
  1. Open a terminal inside that repository's folder - its main checkout, not a second copy of it.
  2. Run `"<path to thor2>/target/release/install.exe" --register-root --db "<path to thor.db>"`. Use the full path to the installer, and for `--db` the memory your assistant's hooks use: it is the path after `--db` in the hook commands `install` wrote into Claude Code's `settings.json`.
  3. It answers `registered '<project>' -> <folder>`, or `= '<project>' is already registered here (<folder>) - nothing to do`.

  `--register-root` records the folder and nothing else - no settings, no hooks, no code reading - and refuses to run without `--db`, so a registration never lands in a memory your assistant does not use. Two answers mean you are in the wrong place, and neither changes anything. "'<project>' is registered at <folder>, which is still a checkout of it": you are in a second copy, and that folder is the one THOR uses, so there is nothing to do. "'<project>' is registered at <folder>, which still exists. Moving a registration is the owner's call": the project moved but its old folder is still on disk - remove or rename the old folder, then run the command again from the new one. A registration moves only once its old folder is gone, so a second copy can never take a project over. For seven days after a registration is made or moved, the project's session start says so in one line, and `doctor` lists every registered working copy, plus every project that owns rules but has none, with the command to run.
- **A command check reaches every part of a command, and matches whole words only.** A check on a command used to read only the start of a call, so `cd /srv && docker exec ...`, a second line, `echo x | ...`, `ssh host "..."`, `bash -c '...'`, `$(...)`, a loop, or `sudo` or `timeout` in front walked straight past it - while a literal it did read was found anywhere, even inside a longer word. Both change together. A command is now split into its parts the way a shell reads it (separators, new lines, pipes, quoting, heredocs, nested commands, and the `ssh`, `sh -c`, `powershell -Command`, `cmd /c` and `eval` wrappers), and a rule bound to a command reaches every part that runs it, in Bash and in PowerShell. A literal now matches only as whole words: `--force` no longer matches inside `--force-with-lease` (it still matches `--force=true`), and `ssh` no longer matches `sshKey.mjs` or `~/.ssh/`, while `/usr/bin/ssh nas` and `Co-Authored-By: ...` still match. A command written with `.exe` in a rule reaches only a call that names that `.exe`, so `install.exe` never reaches `install -m 644 a b`. Text that only mentions a command - `echo "..."`, `grep "..."`, a heredoc of data, a remark after `#` - is not a call of it. A part run in another project's checkout (`cd ../other && git push`, `git -C ../other push`) is judged under that project's rules, and a `cd` into a folder that belongs to no project keeps the session's own. The guard on shell writes reads the same parts, so an `rm` of a guarded file on a later line, inside `$(...)` or inside `bash -lc '...'` is caught too. The checks on a file's content (`contains`, `absent`, `absent_all`) and the answers a `requires` check asks for keep matching plain text, as before.
- **A `requires` trigger can name a family of names, and asking a program for help is never refused.** A trigger is matched as whole words too, so `/thor` never saw `/thor-probe-eval` or `/thor2`: a name that goes on after the trigger is a longer word. End the trigger with one `*` to make it a prefix: `/thor*` catches `/thor-probe`, `/thor2` and `/tmp/thor_new` - and, the stated price, `build/thorough`. The write gate allows the `*` only as the last character of a trigger inside the command, and judges the part before it for being specific enough. A call whose only words after the command are `--help`, `-h`, `-?`, `/?`, `help`, `--version` or `-V` asks the program about itself and runs nothing, so a `requires` rule never refuses it; a `forbidden` ban still does.
- **A session keeps its project's guards when its folder wanders.** The hook read a file check against the folder the session stood in, so an agent working in a subfolder of a repository could remove a line a rule requires at the top of it, and a session whose `cd` stuck in a folder outside every project lost all of its project's guards. The hook now resolves a file check under the top of the checkout and reads a relative path against the session's folder; in a folder that belongs to no project it keeps the project the session last worked in, with that project's registered working copy for its file checks. A folder that belongs to another project still switches to that project's rules.
- **A refusal counts as proof only when a real session shows it.** The proven label trusted any refusal on the log under the hook's name, and a payload piped into the hook by hand makes one too. Now a refusal counts only when it happened in a Claude Code session whose own transcript holds that tool call and the hook's block of it, naming the rule. Each refusal is checked once, at that session's `Stop`, and the answer is recorded in the log, because Claude Code clears old transcripts. A hand-fed payload, a made-up session, or a tool call id copied from a call that was let through never counts, and `doctor` counts every refusal that does not, and why. A refusal only ever sets the proven label: it settles nothing by itself.
- **`serve retest` asks the trial again, for one rule, a project or all of them.** `serve --db "<path to thor.db>" retest --id <id>` runs the same trial on a rule as it stands now, against its registered working copy and the real calls in the log - never a folder named on the command line, so the answer is the same from any folder. It prints the working copy it used, every form it tried and what the hook did with it, and the verdict: rule track, note, blocked, or the one fix only a writer can make. It writes nothing unless you add `--apply`, and then only while the rule is still exactly the one it tried. `--project <name>` and `--all` try every rule and orientation that has no current verdict. The exit code says what it found: 0 a verdict it can write, 3 blocked, 4 a fix for the writer, 1 an error, 2 a mistyped command. `backfill_teeth` is now the same loop over a whole store, and no longer takes `--root`.
- **One reader decides what is settled, and what is undone is counted whatever its weight.** The evaluation filing gate, the Stop hook's teeth question and `doctor` now read the same answer. A rule is settled when the trial's current verdict - a rule or a note - still matches its text, anchors, check, project and severity; while a blocker holds it (its project has no registered working copy, or the registered checkout is mid-change while the default branch still has the line its check needs); or once it is retracted or archived. A tag, a written reason, an open point or a refusal on record settles nothing, and lowering a rule's severity no longer takes it out of the count. This replaces the older ways to settle a rule: a check that bit, a `no-literal` reason, a wired check carried by an open point. The Stop hook names each undecided rule with the `serve retest` command that decides it. `doctor`'s teeth lines now count every live rule and orientation with no current verdict, with the heavy ones beside that; the verdicts - proven, wired, notes by dispute and notes with a pending check, rules kept by `accept_refusing`, wired literals no real call ever carried, and blocked rules per project; which refusals count as proof, and why the others do not; rules taken off the rule track in the last 30 days; and rules refused for a tooth and then stored as a note that no longer names it.
- **Weakening any rule needs a reason, not only a checked one.** `revise` asks for `because` whenever it takes something a tooth could come from away from a rule or an orientation, checked or not: a flag, a quoted call or a backtick span leaving its text; a command, path or folder anchor removed or replaced; its check changed or cleared; its severity lowered; or its kind changed to a report, which takes it off the rule track exactly like a retract and is listed by `doctor` the same way.
- **THOR's own names are reserved at the store.** The actor names THOR writes under itself - `installer`, `retest`, `teeth-write`, `attester` and the rest, and `hook` for every writer but the hook itself - are refused for every other writer, through every program, not at one door only; `model --actor` and `serve hook --actor` refuse them up front with the same sentence. A project's registration record takes events from the installer only, so no retract or revise from anywhere else can move it or remove it.
- **A copy on a second machine refuses what it can already judge.** A replica has no working copy to try a rule in, so the trial runs when the write is drained into the main machine, which now tries it against the project's registered working copy. What the replica can judge on the spot, it refuses on the spot instead of queueing: a literal the text never names, a note label beside a check, a hand-written `teeth:` label, a reserved id, an unexplained weakening. An evaluation report is always refused there, since it is filed on the main machine, in the session that ran it. A queued write the drain refuses is counted by `doctor` on the main machine.
- **An evaluation report counts only once THOR has checked how it was filed, so every project owes one fresh evaluation after this upgrade.** The first Stop of the owner's own session after a new evaluation report checks it once, from the memory's log and Claude Code's own transcript of the session that filed it, and writes the answer to the log: the filing must be a THOR tool call of that session that THOR's hook saw, for an evaluation THOR started in that same session and whose start note that session was shown, with the machine section exactly as the log gives it and nothing on the evaluation's lists changed behind it. Reports filed before this version carry no such call, so they read as not counting, and each project is asked for one new evaluation; the ask names the report on file and why it does not count, and `doctor` names every such report with its reason. Editing `eval-debt-state.json` no longer silences the ask: the Stop hook takes the time of the last evaluation from the log at every Stop. When a session's transcript is gone, its report does not count; when a Claude Code update writes transcripts in a shape THOR cannot read, no report counts and no evaluation is asked for, and every turn says so until THOR is updated.
- **Every write says which session made it, and only a real tool call clears debt.** `remember`, `revise`, `retract`, `mark`, `pin`, `unpin` and `resolve` now store the call's id, a digest of what was sent, and the session the tool server runs in; the hook notes in flight that it saw a write. At the session's `Stop`, THOR checks each new write once against Claude Code's own record of that session and writes the answer to the log. A verdict counts toward the judgement debt only when it was made with `mark` inside a real session, and every reply to a write now names the log position it landed at.
- **A verdict given with `serve mark` from a shell no longer clears judgement debt.** It is still written and kept, but it counts as outside an attested call: it clears nothing, it does not shrink an evaluation's judgement list, and `doctor` counts it on a line of its own. Every verdict given before this release is of that kind too, so after the upgrade the judgement debt is larger than before, by exactly the verdicts `doctor` lists as outside an attested call; they are given again, with `mark`, in the next evaluation.
- **An evaluation report is filed only through THOR's own tool, and THOR writes the facts in it.** The model command line, a second client, a script and an older program are refused, and if one slips through, the report does not count. What was judged, what the machine decided, what was refused, which writes bypassed the tools and which open points were carried are written by THOR itself, from its log, in front of the agent's text; that machine section cannot be edited afterwards. The text the session files is only its plain-language summary and its remarks. The filing is also refused while THOR is still deciding the old rules, or while the verdicts given in the same turn are not checked yet; both say to end the turn once and file again.
- **Who is asked follows the project's work, not one session's clock.** A project's own work clock adds every session together, parallel sessions counted once, and only a new report that counts resets it. A session is held only when it has at least ten minutes of its own work in that project, never on its first Stop there, and not while another session is running that project's evaluation (at most an hour; it gets one line instead). The ask follows the work, not the folder: a session that worked in project A and then moved to another folder is asked about A, and the ask says so. A project with activity in the last seven days and no evaluation that counts in seven days is due whatever the clock says, so an edited clock file can delay the question but never cancel it, and the Stop hook also reads the session's own minutes from Claude Code's record of it. A second cadence, once a week or daily while a project shows rot, is built and switched off: it is a constant in the code, not a setting, it is the owner's decision to turn on, and `doctor` names which one runs. When a Claude Code update writes its record of a session in a shape THOR cannot read, nothing counts, no evaluation is asked for, and every turn says so until THOR is updated.
- **`doctor` shows how the evaluations went.** An `evaluations` line names the newest report that counts and which session filed it, the last five with how their verdicts split (useful, noise, skipped), a flag on ten or more verdicts that all went one way - a blind pass looks exactly like that - and every report on file that does not count, with the reason. New lines name the cadence, the open points THOR wrote apart from the legacy ones, the owner queue against its budget of 8, and a work clock that disagrees with the session records by more than a quarter of an hour. Rules saved with `legitimate_calls`, `may_change` or `accept_refusing` stay listed for the owner.
- **The count of refusals that really happened starts low.** A refusal counts as real only when its tool call id is found in the session's own record, and refusals recorded before this release carry no tool call id, so none of them can be shown to be real. The count grows again from now on, as each new refusal is checked once at its session's `Stop`; nothing is lost, and nothing settles on a refusal anyway.
- **A reply the Stop hook holds for its shape no longer hides the evaluation ask.** When the reply check held a Stop (too long, no summary first), the Stop ended there: the evaluation was never asked in that turn and the Stop was not even counted, so a session whose replies were always held was never asked at all. Every Stop is counted now, whoever holds it, and when an evaluation is due its ask comes in the same message as the reply check's reason - neither one is skipped.
- **A session cannot prove a rule's teeth by tripping it on purpose.** A refusal the evaluating session runs into during its own evaluation, and a refusal in the session that wrote the rule's check, is still recorded but never counts as proof that the rule works in the field: `doctor` lists these apart as "refused during the session's own evaluation - not proof" (or "in the session that wrote the rule's check"), and the report's machine section says how many of its refusals were the evaluating session's own. A session that plants such a call before its evaluation starts, on a rule someone else wrote, still cannot be told from a real one; a refusal only ever makes a rule "proven" instead of "wired", it settles nothing.
- **An old rule with no project and a file check is held for the owner, never handed to the agent.** Such a rule has no working copy anywhere to try its check in, and the only ways an agent had to get it off an evaluation's list were to tie a rule meant for every repository to one project, or to delete a check that is true. THOR now counts it as blocked, keeps its check, and names it in ONE open point for the whole memory - not one per project - for the owner, with the one safe way on: give it a project only when it really is about that project. Every project's evaluation holds these rules by that one point, it waits in the owner queue once, and it does not count toward any project's budget of 8. A new rule with no project still cannot attach a file check.
- **A short session is no longer held for old rules it never touched.** The question about rules THOR's trial has not decided yet now waits until a session has done at least ten minutes of its own work in the project, and it never holds the session's first turn-end there - the same two terms the evaluation ask has. Before, a quick task session could be held at its very first turn-end to decide a backlog of rules unrelated to its task.
- **Setup, an unstored decision and a crowded note no longer hide the evaluation ask either.** When one of those held a turn-end, the evaluation was not asked in that turn. Now, when it is due, its ask comes in the same message, after that reason, and the turn-end is counted once.
- **A file check that cannot be anchored because the place is full is held for the owner, never handed to the agent.** An old rule whose `path_exists` check names a file the rule is not anchored to used to land on the agent's batch with "anchor the rule to that file, or drop the check"; when four facts already sit on that file the anchor is refused, every other way out folds or archives one of the owner's facts, and an agent cleared the true check to file. THOR now counts such a rule as blocked, keeps its check, and writes one open point naming the full place and every fact on it, for the owner to fold, move or archive; once the place has room the rule is the agent's again.
- **A check cleared or moved during an evaluation is reported.** The evaluation report's machine section and `doctor` now list every rule whose check an agent cleared, moved to another file or changed (with its reason), and count them; before, the section said nothing and only the rule's own history showed it. THOR's own verdicts that drop a check are not listed.
- **A long chat-only turn is no longer reported as a transcript THOR cannot read.** The warning to tell the owner fired for any turn with no tool call whose transcript passed 64 KB, which the context injected into a session alone can reach. It now fires only when THOR fails to read tool calls it expects: calls in a shape it does not know, or a filing it can prove was made.
- **The retest command a hold prints can be run as it stands.** It was printed in PowerShell form (`& "C:\...\serve.exe" ...`), which the evaluation routine's pre-approved shell commands never matched, so a headless session was refused again and again. It is now printed with forward slashes and no `&`, in the one form the routine's `allowed-tools` entry allows, and `install` writes that entry into the routine it seeds.
- **The shipped evaluation routine is rewritten to match, and an installed copy is not overwritten.** `install` writes `/thor-eval` only when none is there, so a routine written by an earlier release (or a copy of it you edited) keeps telling a session to file open points, to send `trial_check` (an unknown argument now) and to settle rules with written reasons, all of which THOR now refuses or ignores, and an evaluation run by it would loop against the gate. To use the new one: 1. Find `thor-eval.md` in the `commands` folder inside Claude Code's own `.claude` folder in your home folder. 2. Rename it to `thor-eval.md.old` (nothing is lost). 3. Run `"<path to thor2>/target/release/install.exe" --db "<path to thor.db>"` once more; it writes the new routine and says so. 4. If you keep your own routine under another name, copy the new steps into it by hand (the file is `thor2/eval-command.example.md`); its steps 2 and 4 and the last two sections are what changed.
- **A PowerShell call is no longer cut at the `)` that closes `@( ... )` or `.Method( ... )`.** In the PowerShell dialect a `(` right after a character of a word (an array `@('-File','x.ps1')`, a method call) was read into the word, but its closing `)` always ended the command, so the flags written after it stood in another command. `Start-Process -FilePath p -ArgumentList @('-File','x.ps1') -WindowStyle Hidden -Wait` then lost `-WindowStyle` and `-Wait`, and the two rules that require those flags refused a call that carries them: on the owner's own record 55 of 558 distinct `Start-Process` calls were refused for a `-WindowStyle` or `-NoNewWindow` they carried, and 56 for a `-Wait` they carried, and the same cut also split `$($x.Trim())`. Such a group is now one word of its command, like `$( ... )`, and what it runs is still read as a command of its own, so a rule on a command inside the array still reaches it. A `(` that starts a statement (`(cmd1; cmd2)`, `if (...)`) is unchanged, and so is Bash.
- **`doctor`'s "literal never carried" count no longer lists rules it cannot judge or that really bite.** It listed every wired rule the trial gave no proof, but a `requires` check has no literal to carry (the count is zero for it by construction), and the call corpus drops every call a session was refused for, so a rule that really refused calls looked like one nothing ever carried. The line now counts wired forbidden rules only, and leaves out a rule a real Claude Code session was refused by; its wording says so. On a copy of the owner's store the count went from 61 to 18 (30 requires rules and 13 forbidden rules that had refused real calls).
- **`doctor` names the rules whose command anchors have never fired and that no call can reach, and a write says so when it adds one.** A rule bound to a command fires at a call only when the call's own first word starts with it (or a tool call's whole name equals it), and at the owner's prompt when the prompt contains its word or phrase. An anchor that is a stored sentence ("Raspberry Pi 5"), a tool's short name (`remember`), a fragment without its program (`push --all`) or a program that is gone is therefore not dead by itself - it fires when the owner types it - but if nobody ever does, the rule fires nowhere and nothing said so. The new `command anchors never fired` line counts the live rules whose command anchors have ALL never fired, on a real call or on a prompt of the owner's, and that no call can reach; it says how many have no other binding, counts them per class (a bare tool name, a flag first, a fragment of a longer command, never reached and not a program here) and names each one with its anchor and the class, `--full` lifting the 20-name cap. Never listed: an anchor that any real call or any owner prompt in the log ever fired, a program found on `PATH` or in THOR's own `bin` folder, a PowerShell cmdlet, a shell builtin, a tool name the hook sees (`Agent`, `mcp__...`), or any program a real call ran (so a command that lives only on another machine is not called missing). `remember` and `revise` add a note, never a refusal, when a NEW command anchor is of the same kind: it says what the anchor does match (calls that start with it, and the owner's prompt containing it) and offers the fix that fits what you meant - a program word first, the whole tool name, a path or a moment, or leaving it as the keyword it is.

**Upgrading from 2.4.1 or 2.4.0**: close your assistant, so none of the programs is running, and unpack over the old ones. Then register the working copy of each repository you use with THOR, once, from inside it: `install.exe --register-root --db "<path to thor.db>"` (the steps are in the entry above). Start your assistant again and run `doctor --db "<path to thor.db>"`: its `working copies` line names any project that still owns rules but has no working copy registered. Every rule written before this release has no verdict from the trial yet, so `doctor` counts it as undecided; THOR decides them itself at the start of each project's next evaluation (up to 20 seconds per start, so a large backlog takes several evaluations) and hands an agent only what needs a fix of its own. Every project owes one fresh evaluation after the upgrade, because no earlier report can show how it was filed: the next ask names the report on file and why it does not count. Replace the evaluation routine too (see the entry on the shipped routine above). `serve --db "<path to thor.db>" retest --all` shows what the trial would decide for every one of them and writes nothing - read it before you run it again with `--apply`, because a rule whose old check no longer bites becomes a note without that check.
- **A fact is shown in full once per context, then never again.** A session's main conversation, and each subagent on its own (a fresh context has seen nothing), gets a fact in full one time; there are no reminder lines, and a prompt the owner types opens no new showing. Only a new session start (also a resume or a compaction) shows it again. Two facts that say the same in one block are shown once. Every refusal still runs, and only a full showing counts as a serving.
- **No Stop holds a turn for a judgement or for old rules.** The "N item(s) have fired repeatedly" hold and the rule-upkeep question are not asked at the turn's end; both are asked inside the project's evaluation (its frozen judgement list, its batch and its A4 list), at most once per 16 hours per project. The 40 means 40 sessions, not 40 firings: a fact counts once per session toward the verdict it owes. Holds about the session's own writes, setup, a stated decision, the reply rules and the evaluation ask itself remain.
- **One project runs one evaluation at a time.** A second session's evaluation of the same project does not start while the first one's session was active in the last 30 minutes; that session gets one line naming the session that runs it. Once the running one has been quiet for 30 minutes, the next ask takes the evaluation over and closes the old one as superseded, never voided: its verdicts and edits stay. Another session's attested edit of an item on the lists never voids an evaluation; the item counts as settled by that session.
- **A turn held for the evaluation is held again until the report is filed.** Once the session did something since the hold, it is asked to file in that same turn, and it lets go only after nothing more is done, with one line saying the report is still owed.
- **The start note shows where each judged item fired.** Every item on the judgement list carries how often it fired in this session and its last few places (the command or file), and `get` with `fired: true` lists an item's recent firings in the calling session. The place is the part of the command around the item's own anchor, a prompt shows the anchor or moment word that matched (never the prompt's text), and an Agent or MCP call shows its tool name.
- **A rewording never clears a true check.** A text-only revise of a rule whose check holds but whose bindings never reach its file keeps the check, stays undecided and names the rebind as a step of its own. A reason tag beside a working check is refused on a reword too, and a flag a rule recommends ("use git grep --no-index there") is never given a forbidden tooth.
- **A full place is the agent's to clear.** A rule whose check needs a full place goes to the agent's batch with every note on that place (its severity and whether its check can refuse) and the three honest exits - fold, move to a narrower anchor, retract a stale one with a reason; only when every note there is a heavier rule whose check can refuse does it stay THOR's own open point. Open points are no longer put in front of the agent: the session start carries one line with their count.
- **The owner's go cannot be typed by an agent.** A requires check tagged `owner-approval` is answered only by the owner's own message in this session, this turn or the one before - never the call itself, a subagent's hand-back or quoted text - and an unreadable transcript refuses.
- **Stop notices that do not hold the turn no longer hold it.** The void notice, the "running in session X" line, the "report still owed" line and the Response Guard's warnings reach the owner as a plain message, and are queued for the agent's next prompt (at most three, each once).
- **A call that trips several requires rules is refused once, naming all of them,** and a revise is refused once with every problem. A requires check looks for its required words only in the command that trips it, never in another command of the same line.
- **A negated action is no moment, and other parties' messages are not the owner's prompts.** "niet pushen", "no deploy" and "don't push" draw no push or deploy facts; a message from another session, a hand-back, a task notification or a local-command echo draws no facts and raises no capture flag. A reply that denies a push is no claim of one. A bare generic word in a prompt (such as "dev", "src", "test", "docs" or "server") no longer draws a fact anchored at a path; the path itself (`site/dev`) or a distinctive segment still does.
- **The session start fits what Claude Code shows.** Claude Code keeps a hook output over 10,000 characters in a file and shows the agent only the first 2 KB, while THOR used to count every rule as shown. The block is now cut to 9,500 bytes at whole rules, the heaviest first and a rule of this project before a global one, ends with one line saying how many did not fit, and only the rules really in it count as shown. Every other hook output is cut the same way.
- **The "N more apply here" line names ids, not a command.** It used to quote the whole tool call, and a long shell script made a 17 KB block.
- **doctor shows the volume and a failing backup.** For the last 24 hours and 7 days: facts shown in full, repeats left out, the five most shown facts, what session starts carried and how many Stop holds a session gets on average. A failing backup says "backup to <repo> failing since <time>: <reason>".
- **The backup stays under GitHub's file size limit.** The event log is exported in numbered segments (`events-0001.jsonl`, ...) of at most 50 MB; the old single file leaves the export in the same commit; `backup --restore-from` reads the folder (or the old file name) and verifies every hash as before. A failed attempt is not retried at every session start for an hour, and a local backup commit holding a file GitHub will never take is replaced, never force-pushed.
- **The Response Guard names no stored note.** Its message no longer quotes ids such as "(mcp-9caf0748)", and a rule can carry `asked_for_any_of` and `reminder_if_asked`, so the length rule stops saying "no test counts" when the owner's own prompt asks for the test result.
- **The trial of a rule counts only calls the hook would refuse.** A call run in the folder of another known project, or made by a session that last worked in another project, is not this project's business; the trial store now knows the other projects, so a project's push ban no longer counts pushes made in other repositories.
- **THOR's own housekeeping at a session start carries no session's id,** and the crowding hold ignores writes THOR made itself. The owner's prompt text is not kept in the log.
- **The backup follows a remote called `nas`, and `--remote` names another.** A private copy of the memory can live in a bare repository on a NAS instead of on a website. `backup` now picks its remote by itself - a remote called `nas` in the backup folder, else the one the branch already follows, else `origin` - so the SessionStart hook and the hourly task did not have to change, and `backup --remote <name>` chooses one on purpose (a name the folder does not have is refused with the fix). A commit that never reached the NAS is pushed on the next run, and a local commit holding a file over the limit is still replaced, now measured against that remote. `doctor` always prints where the last copy went and how long ago, and says since when it has been failing and why. The old remote is no longer pushed to and is left as it was.
- **An `absent` or `absent_all` check over a folder no longer dies on one binary file.** A zip or an image beside the text files made the whole folder "unreadable as text", so the check could not be tried, "name the literal" was refused, and a true guard had to be cleared. The folder is now read lossily for those two kinds (an ASCII literal survives a lossy read, so no `Holds` is ever false); an oversized or unreadable file still makes it `CannotRun`, and `contains` stays strict.
- **The trial sees most calls whole, and a call the log cut is "unknown", never safe.** The log kept 120 characters of a command, so most real `ssh ... docker exec ... sh -c "..."` calls were cut and "would refuse 0" was read as a safe tooth. It keeps 400 now; a call an older build cut is still recognised, and the receipt says "unknown: N of M reached call(s) not tried" instead of folding them into a zero. A cut call whose kept part already carries the literal counts toward the more-than-half refusal.
- **Hanging THOR's own suggested check no longer trips on a `no-literal:` tag.** A `revise` that hangs a check that refuses, and leaves the tags alone, drops the reason tag itself and says so; naming the tags and keeping the reason is still refused as the contradiction it is.
- **One count of what is owed, and a warning for a stale tool server.** The ask at the end of a turn, the filing reply and `doctor` read the same count and call it "owed store-wide" next to the evaluation's own list. `doctor` also names a running tool server that started before its program was replaced, and says to restart Claude.
- **Filing no longer costs a turn end for rule writes already on disk.** When an evaluation report is filed, the writes of that turn that are fully in the transcript are attested on the spot (only positive answers are recorded, so nothing is marked a side door early); a verdict still waits for the Stop, and the refusal says why.
- **The words about a contains check match what the hook does.** It guards writes to its own path, and only for a rule that carries some file or folder anchor, which need not be that file.
- **The machine section counts only the evaluating session's trial refusals,** and names the others apart.
- **A tooth is no longer derived from a piece of the anchor's own path, a bare `-n`, or a verb that describes a flag.** "README" in README.md, "RELEASE" in RELEASE-CHECKLIST.md and "-n" beside a longer literal derive nothing, and the present tense (`draait`, `runs`, `gebruikt`, ...) reads as a description of the flag, not a prohibition of it.
- **A refusal that answers several rules at once is logged once per rule.** The hook read the rule id out of the first line of the refusal, and a combined "answer ALL of them" message opens with a count instead, so such a refusal wrote no record at all: `doctor` never counted it and the transcript check could never verify it. Each rule the message names now gets its own `gate_refused` event, and the transcript check accepts a block that names the rule anywhere in a combined message.
- **A brief that names one absolute working path answers the parallel-agents rule too.** A rule cannot tell one agent from several (a call sees only its own input), so `parallelle-agenten-eigen-scratchpad-submap` refused a single background agent. Its answers now include "absolute path" for the single-agent case; a separate scratchpad folder or read-only stays the answer for parallel agents.
- **A fact tagged `interactive-only` is kept out of a headless session.** Some facts are written for the owner's chat (delegate everything to background agents, answer before starting an agent, paste prompts). A `claude -p` run that was served them delegated to a worker that could get no shell permission and delivered nothing. THOR now reads how the session was started (`CLAUDE_CODE_ENTRYPOINT`, else the head of the transcript; every `sdk...` entrypoint is headless) and leaves a tagged fact out of that session's start block and its prompt facts. Facts that fire at a tool call or a file are not affected, and a session of unknown kind is served as before. Each session start writes one `entry` line in `volume-log.jsonl` saying what it saw. To tag a fact, add `interactive-only` to its tags with `revise`.
- **The session start block puts what this project has been using first.** The block is still capped at 9,500 bytes with the "did not fit" line, but the facts shown at a prompt or before a tool call in this project's own sessions in the last 14 days come first, then the other heavy rules (this project's own first), then the rest. (The order is refined by the entry on whose fact it is, below.) Field test 6 found 28 of 33 start facts beside the point of the task.
- **A secret typed in a command no longer goes into the log.** The place a fact fired, and the command of a refusal, are stored with likely secrets replaced by `[redacted]`: an Authorization header value, the value after `=` or `:` in a name holding token, secret, password or key, the value after `--password`, `--token`, `--secret` or `--api-key`, well-known token shapes, and long hex or base64 runs. It looks for likely secrets and never claims to find all of them.
- **The working copy line and the open-points count line are shown once a day per project.** They repeated at every session start with nothing for the agent to do. The banner for an owner queue over its budget still shows at every start.
- **The answer-length hold quotes the owner instead of guessing the request.** It used to say the owner asked for "the test result", so an agent dropped the "what you changed" the same prompt also asked for. A reminder in `guard-response-rulebook.json` may now carry `{owner_request}`; the hold fills it with the sentence of the owner's last prompt that names one of the rule's `asked_for_any_of` terms (else the first words of the prompt), and the shipped text says to keep every item the prompt asked for, and to keep the changed files or places when the prompt asked what changed.
- **A call that only looks no longer draws advice about changing things.** A Bash call whose every part only reads (`cat`, `grep`, `rg`, `head`, `tail`, `ls`, `find` without `-delete`/`-exec`, `sed` without `-i`, `git log/status/diff/show`, no redirect) derives no push, publish, deploy, install, commit, delete, send, spend or configure moment, and a fact reached only through a file it names is served only when its text names the running tool (a fact about reading with `grep`). `cat server/package.json | grep test` served four facts about version stamps and the lock file; it now serves none of them. An anchor on `package-lock.json` never matched `package.json` (the path match is on whole path segments); a test now pins that.
- **The session start block is ranked by whose fact it is.** This project's own facts first, then the global heavy rules, then house style, then global facts with no weight at all; what this project's sessions were shown lately goes first inside each step. A headless start also leaves out facts whose only binding besides "always" is answering or claiming done, records how many and which it left out (interactive-only too) on the `entry` and `start` lines of `volume-log.jsonl`, and carries neither the working copy line nor the open-points lines.
- **A real commit whose short form is all digits counts as a commit.** The check of a "verified" claim only treated a sha as one when it held a digit and a letter, so about one commit in forty-three (a first eight characters of digits) never counted. A run of hex digits written right after "commit", "sha", "hash" or "rev" is now asked of the repository, whatever its letters; a bare number is still a number.
- **A Stop hold's own text is no longer read as the owner's prompt.** After a hold, Claude Code writes the hold's text into the transcript as a user line (flagged `isMeta`, opening "Stop hook feedback:"); the guard read that as the owner's last prompt, so the next check judged the reply against THOR's own words. Such a line is now skipped.

- **A refused removal says how to go on, and a proxy check is no longer called proven.** A `contains` refusal now says that when the owner asked for the line to go, the rule's check is revised (with a because) or the rule retracted first, and never kept alive in a comment. The trial counts the literal in the committed file as evidence only when the rule's text or falsifier names that file; otherwise the rule is wired, not proven.
- **`2>/dev/null`, `>/dev/null`, `NUL` and `2>&1` no longer make a call a write.** A call that only reads and discards its errors is read-only again, so it draws no advice about changing the files it names. A redirect to a real file still counts as a write.
- **The length hold quotes the sentence that asks for the report.** It picks the sentence(s) with a report verb or one of the rule's terms, else the last sentence, and cuts at a word boundary. The shipped rulebook asks for more terms ("wat je veranderde", "hoe je het controleerde") and its `reminder_if_asked` no longer assumes a test result.
- **A headless session start carries at most eight global facts.** The project's own facts all stay; the irreversible and costly global facts come first. The volume log's `go`/`gi` name what was cut.
- **A claim of checking is evidenced by a check the turn ran.** A "checked" claim passes the evidence rule when the same turn ran a syntax check, test run, build check or diff through a shell tool, or the answer names one. The shipped reminder is English.
- **Two holds on one reply are one short hold.** When two rules of one tier fire, each says its requirement once in a `short_reminder`, and one line keeps any note about a refused edit or a forced change.
- **A command quoted inside a prescribed route is no longer forbidden.** A rule that prescribes a route ("pipe it via `... | ssh host 'sh -s'`") had a forbidden tooth built from the command inside the quoted route (`-s` on `sh`), because the word that recommends it stands before the whole backtick span, out of reach of the three words read before a command; the tooth then refused the very call the rule prescribes. A recommending word before a span now counts for the commands inside it, unless a negating word stands anywhere in the same sentence, and `via` and `through` are recommending words. Measured over the 1756 live rules and orientations, one rule's derived teeth change. The evaluation report's machine section now says a check was cleared, moved or changed "by an agent's write rather than THOR's own trial" (it read "by a write that is not THOR's own", which the attested agent calls under it contradicted).
- **A placeholder in angle brackets never becomes a tooth.** A rule that shows a call with a stand-in in it (`git -C <path> reset --hard`, `ssh -i <keyfile> user@host`) had teeth built from the stand-in itself, such as forbidden `<path>` or `-i <keyfile>`. No real call ever carries that text, so such a tooth could never refuse anything, yet it was reported as wired and the evaluation was told to hang it. A literal holding `<` and a name and `>` (a letter first, then letters, digits, spaces, dashes or underscores) is no longer derived from a rule's text. A `<` that opens no placeholder (`<<EOF`, `< file`, `2>&1`) still works as before.
- **A `contains` check on a phrase that sits only in comments is no longer hung.** Measured on a copy of the live store, 7 of 339 `contains` checks had a literal found only on comment lines of their file, so the tooth guarded nothing the rule is about and would have refused a harmless comment cleanup; one such rule was seen live on 2026-10-03, hung after THOR forced the writer to hang a tooth it had built from the text. At write time, a new or changed `contains` check whose literal sits only in comments is now stored as a note, and a `contains` tooth built from the text on such a literal is not built, so it forces nothing; the reply says why and how to keep a check (point it at a documentation file, which is never read as comments, or at a literal that also occurs in code). Nothing already on the rule track is demoted: a retest is unchanged, and a revise that keeps a check the rule already carries keeps it. The comment test is the one the warning already used (`model::check::looks_like_comment`), now shared.
- **A sentence of the owner's is never replayed as a real call.** The prompt surface records its firings with a place like `(prompt) word`, and those landed among the real calls a rule's trial replays, so "reaches N whole real call(s)" counted the owner's own words as commands (measured on a copy of the live store: an anchor `prompt` reached 17 such pseudo-calls, `backup` reached one of 6). They stay out of the corpus now; the words a prompt fired on are still remembered for the never-fired anchor check, and the 17 slots they held in the 20,000-call cap go back to real calls (on that copy, 2 anchors doctor called never fired are now seen to have fired).
- **A recommending word that opens a clause now covers the first quoted call of that clause.** "Gebruik op de NAS `sudo docker compose -p x up -d` - kaal `docker compose up -d` botst" prescribes the first call, but the recommending word stands four words before it, outside the three-word window, so THOR derived "forbidden '-p'" on `sudo docker compose`, the opposite of the rule. A recommending word that is the first word of the clause now counts for the first backtick span of that clause. The clause ends at a dash, colon, semicolon, sentence stop or a word such as "but"/"maar", so a contrasting clause keeps its own reading, a second span is never covered, and a negating word anywhere in the clause cancels it. Measured over the 1713 live rules and orientations in a copy of the store, one rule's derived teeth change (`node-test-zwijgt-bij-een-hangend-verzoek` no longer forbids `--test-reporter`, which it prescribes).
- **A release now runs its own packaged programs like a new user before it can be published.** Until now no step ever executed a packaged file: a bundle built without meaning search, or a hook pointing at a missing program, would have shipped silently. Each asset is unpacked on its own runner and walked through the setup steps in a throwaway home (install, hooks and tool server written, doctor, a second install that changes nothing, a note stored through the tool server and served back at session start). `publish` waits for all three. To run it yourself: `cargo test --release --features semantic -p ops --test release_smoke -- --ignored --nocapture`.
- **A date or version after "regel" is no longer read as a line number.** The write gate refused a rule text for naming a specific line when "line" or the Dutch "regel" (which also means "rule") was followed by any token starting with a digit, so "Harde regel 2026-08-23" was refused for naming a date. Now only a plain integer after the word counts ("regel 93", "line 93:", "(line 93)"); a date, a version, a time, a percentage or a decimal after it is let through. The "L93" and "file.rs:93" shapes are unchanged, and a range such as "line 93-95" is no longer caught. Run over every live rule and orientation in a copy of the store, no verdict changed.

## 2.4.1 (2026-09-17)

- **A session that starts right after a compaction is told so.** A `SessionStart` payload whose own `source` field reads `"compact"` gets one added line: the summary just given is not proof, so anything it calls done, tested, flashed, deployed or live should be checked again first. It never fires for any other source, and never for a subagent.
- **The evaluation starts with the previous report's open points.** Before judging what fired, it looks up the newest evaluation report filed for this project and either settles what that report left open - unjudged items, gaps, anything still to be probed - now, or carries it into this report's own open points with the reason it is still open.
- **A project worked in for an hour cannot end a turn without a recent evaluation report, only inside a project.** In every project a session has worked in for at least an hour, the Stop hook blocks the FIRST Stop of EVERY turn - not merely once per session - until an evaluation report is filed for that project, before the judgement debt, when both are due, and regardless of how many notes currently owe a verdict. A filed report covers the next 16 hours: a rolling window rather than a calendar day, so a report filed late at night is not undone by the next midnight, and one filed early in the afternoon no longer buys silence clean through to the next morning. Each ask names how many times this project has already been asked and since when. A checkout that resolves to no project is never asked at all, since there would be no way to ever file the report that silences it.
- **Filing that report is not the end of it - but only when something risky happened since.** A new evaluation is due after every three hours of work since the last report, pauses excluded, again as a hard stop until its own report is filed - but only once a real risk has shown up too: three or more code changes with no test or build run in between, or a context summary. Three quiet hours with neither stays silent. The repeat covers only what happened since the last report, plus the state of the work right now, and names the risk that triggered it. "Work" is now measured from actual hook activity, gap-filtered, rather than a single timestamp, so an idle stretch of half an hour or more no longer counts toward either the first or the repeat ask.
- **The shipped evaluation pre-approves shell commands one by one.** The `allowed-tools` frontmatter no longer carries a bare `Bash`, which let any shell command through unasked during an evaluation; it now names the git, test and build commands the routine actually runs, plus the health check.
- **The shipped evaluation now files its own report into the memory**, so a later session (and `doctor`) can see one was done. The 2.4.0 notes below already claimed this; it arrives now.
- **The ship line counts what is waiting and only alarms on a failed attempt.** A healthy hourly ship with nothing new to send still reads as fresh no matter its age; changes waiting behind an old success are named and counted, never mistaken for a failure; only an attempt that actually failed raises the alarm.
- **A backup push that failed is retried.** A commit that landed locally but could not reach the remote is pushed again on the very next run, before that run's own once-a-day schedule is even checked.
- **The evaluation's teeth step tries a check before it accepts that none is possible.** Step 4 no longer lets "it's a judgement rule" end the question on its own: for a heavy fact with no check it now names, in the report, the literal fragment, the file or command it belongs at, and the check kind - and only after that attempt may it answer "no literal", with one of two named reasons. A fact that already carries that reason gets it read again whenever the fact names a command or file. The report states the health check's teeth count before and after the step.
- **A new heavy Rule or Orientation must say how it can refuse, or why it cannot.** Gate ground 11 has asked this of a Rule since 2.4.0; it now asks the same of an Orientation. Remembering one, or revising one so its severity becomes `costly`/`irreversible` or its last check is cleared, is refused when it carries neither a check nor a `no-literal:<why>` tag - the refusal names both honest reasons a "no-literal" answer may give.
- **A version bump without a changelog section fails before a tag ever exists.** CI checks that `thor2/Cargo.toml`'s version has a matching `CHANGELOG.md` section on every push, not just at release; the release workflow then copies that section into the published notes and refuses to publish without one.
- **A directory-only rule's own note stopped reading as a full room.** Every binding on an item being a directory got the same wording as a crowded pool - "stored onto a place that is already full" - and the Stop hook nagged to fold, re-anchor or tag it `crowded-on-purpose` even when the place was never full at all. The two are told apart now: a directory-only note stays exactly as broad as before, but the Stop hook's own displacement check only ever reacts to a genuinely crowded pool.
- **`doctor`'s crowding line now also counts a crowd hiding behind a command.** It used to probe only file anchors; an item bound to a command that a real block would never fully show went uncounted, however many rivals shared it. The line now probes commands the same way, naming an invisible one `<command> (command)` so it reads apart from a file.
- **A repeat verdict is accepted again once the item earned a fresh one.** `mark` used to refuse a second identical verdict on the same id for the rest of a session, full stop - even once the item had fired 40 more times since and `doctor` listed it as owed again, with no way to pay that debt down in the same sitting. It is written again now, once that threshold is crossed, and the reply says how many more times it fired and since which earlier verdict.
- **The dead-on-arrival refusal stopped suggesting a bigger hammer.** Its own fix text used to float raising severity as one of the ways out, which is exactly the compensating knob the evaluation routine forbids - it pushes a heavier warning out to show a lighter one. The refusal now points only at a narrower binding or folding into an item that already holds the ground, and says plainly not to raise severity to win the place.
- **A served item now says where it fired, not just that it did.** `doctor`'s judgement-debt list named an item's binding but never which command or file among what it reaches had actually triggered it, so an evaluation judging "did it belong where it fired" sometimes had no place to look. Every serving now carries its own trigger - the command, the file, or `session start` - and the newest one is named after the binding as `last fired at '...'`.
- **Meaning search keeps itself up to date.** Only what is new or changed gets embedded, what is gone is dropped, and the hourly copy job does it on its own with a budget per run, so a fact written today is findable by meaning within the hour instead of whenever somebody remembered to rebuild by hand. A new `vectors-refresh` command does the same on demand; `vectors-build`'s full rebuild is unchanged. Measured on a real store: a backlog of 705 items took just under three minutes, and a normal hour is a second or two. A failure there can never change the outcome of the copy job it rides along with.
- **A search can be narrowed to one kind.** Both the assistant's own search and the command line take `kind` - rule, orientation, report or chunk, case-insensitive and tolerant of an obvious plural - because a plain search is dominated by reports, whose text runs long. Asking to filter by a register's kind is refused and points at its key instead, since a register only ever answers to its own key. One parser behind both doors, so the two cannot drift apart.
- **A search says when it answered from meaning alone.** If no wording in the store matched your words literally, the reply now says so in one line: that what follows came from meaning search, that meaning search scores whole documents and favours long ones, that a short rule answering the question may be missing entirely, and that two or three distinctive words beat a full sentence. A `kind`-filtered search that comes back empty while the unfiltered ranking had hits says that too, with the count, instead of a bare "no matches".
- **`search --explain` shows why an item is or is not in the answer.** Per hit it prints whether it was a literal match or a meaning match with its score, and it names the floor and the cap once, so the two numbers that decide everything are visible. `search --explain-id <id>` answers the question that used to be unanswerable: that item's own score, and whether it fell under the floor or cleared it and was cut by the cap. Neither flag changes the ranking or the normal output.
- **Meaning search was measured, and the honest result is in the notes.** A new 36-question set, every question a paraphrase with no word in common with the item it asks about, finds the right item in the shown block for a quarter of the questions. Two thirds of the misses are not close calls: the answering item scores below the floor and sits hundreds of places down. A set of 24 questions the store cannot answer scores its best match a median 0.43 and up to 0.58, which overlaps the real answers entirely, so no threshold separates them. Two candidate fixes were built and measured against that set and both were rejected on the numbers: reserving slots for rules moved one question of 36 at the floor in use, and charging long documents for their chunk count traded reports away for rules. The lever that remains is an embedding model trained for question-against-passage rather than sentence-against-sentence, which is a separate job.
- **A search can ask for several kinds at once, or for everything that can fire.** `kind` now takes a comma-separated list, and `fires` as a shorthand for the two kinds that reach a moment of action. This came straight out of use: the first program to filter on `rule` broke two of its own checks, because the fact that had to steer the action was an Orientation, and asking for both took two searches. A report can never fire at a moment at all, so a warning stored as one is silent exactly when it matters.
- **`hook --diagnose` can say that it could not look.** The hook prints nothing and exits 0 on every failure by design, so an assistant is never broken by its own memory - but from outside, that silence is identical to "nothing applies here". A program driving this boundary itself can now ask: it gets one line on stderr and exit 2 when the payload is not valid JSON, when the memory is not where it was told, or when the run failed internally, and exit 0 with "looked, and nothing applies here" when the silence was honest. A normal run is byte for byte unchanged.
- **A firing now says who it was served to, and only an assistant's firings are anyone's debt.** `hook --actor <name>` stamps the caller on every delivery it records, and the judgement debt counts only what an assistant was actually served - because the standing question is "did this belong where it fired", and the only one who can answer it is someone who was there. A program driving the boundary for a local model no longer leaves a debt that nobody can honestly settle; its traffic stays visible instead, named with its own count in the health check's debt line.
- **A measurement run can leave no trace.** `hook --no-record` answers exactly as a normal run does and records no delivery at all, so measuring a program against this memory hundreds of times cannot quietly bend the counts that maintenance depends on.
- **A program can ask in advance whether something would be refused, and why.** `check --json` and `why --json` give the facts that apply as data instead of prose - `id`, `kind`, `severity`, `text` - and mark each one either a prohibition or advice. A fact counts as a prohibition only when its own machine check's forbidden literal actually occurs in the command being proposed, and the matched literal is named; a heavy fact with no check stays advice, because severity says being wrong is expensive, not that anything is verifiable. The prose form marks the same distinction, and the hook answer carries the same rows beside its existing text so a caller that already asks per action needs no second call. Which form a prohibition arrives in depends on the call: a tool call carrying a command line is refused outright, with the rule and the matched fragment in the reason, while a call with structured arguments whose tool NAME is what the rule is bound to comes back as an ordinary answer with a prohibition row in the data. The second is the only form a program whose tools carry no command line will ever see, so a caller must read both.
- **A heavy rule hanging on a command must try harder before it may say nothing can catch it.** Until now, any heavy rule could answer the "can you refuse something" question with a free declaration that nothing is catchable, and that answer was being given at scale: on the maintainer's own store, 45 heavy rules hang on a command with no check at all, against 31 heavy rules in total that can actually refuse anything. For that one shape - heavy, anchored to a command, no check - the generic answer is now refused, and the refusal names the item's own command against the two checks that can genuinely catch something there: a forbidden fragment that must never appear, or a required answer that must be present for something forgotten rather than written. When neither honestly fits, `no-catch-on-command:<why not>` says so and the write goes through. Nothing else changed: a rule with a check, a light rule, and a heavy rule anchored to a file, a folder, a moment or pinned all keep the answer they had. The health check now counts this new population beside the old one, and the mid-session nudge names, per item, which of the two answers that item needs.
- **`doctor` names the toothless heavy rules and the bare no-catch answers, not just counts them.** A bare count gives nothing anyone can act on, because nothing says which rules make it up. They are now listed the same way `decay_line`'s dead anchors and `judgement_debt_line`'s owed items already are: a handful named, the rest counted, `--full` for everything. The toothless list (a heavy rule that still cannot refuse anything) sorts heaviest severity first, then by how often the rule actually fired since its last verdict. The bare list (a `no-literal` answer with no reason) sorts oldest first, since nothing else ever re-asks it and the longer one has sat bare, the less likely anyone remembers why. A summary count and its own named list are now tested to always agree, for both - the same class of drift `unjudged_line` once had between its own count and its `--full` list.

- **Asking what applies now names every rule that would refuse, not just the four you are shown.** A context block shows at most four notes, and until now `check` and the hook's own machine-readable verdicts only judged those four. A rule that really would refuse your command, but sits behind four heavier ones at the same anchor, printed nothing at all: the only way to see it was `why`. That silence can make a rule look broken while it is refusing exactly the mistake it guards against. Both surfaces now judge every rule that applies, each row saying whether it was shown, and the prose form lists any hidden prohibition underneath the block with the fragment it matched and why it was not shown.
- **A rule's teeth are tried by the tool at the moment it is written, from both sides - and proven only against reality.** Storing or revising a rule that is marked irreversible or costly, or that carries a check able to refuse, no longer takes anyone's word for it. The tool builds two attempts out of the rule's own anchor and its own forbidden fragment: one carrying the fragment, which it must refuse, and one carrying only the anchor, which it must let through. Both holding means the check is WIRED - it reaches the right place - and nothing more: both attempts are built from the writer's own fragment, so a fragment no command will ever carry passes exactly as well as a real one. A rule only counts as a proven guard once the log shows its check biting reality: the real hook refused a real call under it, or a real call the rule already fired on carries the fragment while the rule's ordinary calls still pass. The outcome, never the writer, decides the box: proven, wired but not proven, informing only, one that refuses legitimate use too, or one whose anchor already contains its own fragment. The label is written by the tool and a writer cannot set, clear or forge it. Nothing is ever refused for lacking teeth: the knowledge always goes in, correctly labelled, and the receipt says what was tried, what the log holds, and what would prove it.
- **The teeth question is asked again every time, and only real teeth or a real reason settle it.** Until now the Stop hook dropped a rule from its teeth question the moment it carried any check at all, or any written reason. The question is now derived from what the rule can actually do at that moment, and exactly three things settle it: a check that has bitten a real call on record; a `no-literal` reason that quotes the legitimate call carrying the same fragment, or names the command, file or moment the rule is about; or a wired check carried by an open point that names it, so the next evaluation has to close it. A reason that would fit any rule ("it is a judgement rule") settles nothing, and the gate refuses it on a heavy rule. The question also moves on: the rules asked about least often come first, so a session is not shown the same five every time.
- **Filing the evaluation report is refused while the log still shows the work undone.** The obligation used to lift the moment a report existed, and nobody read it, so a session could discharge a day's review with prose. Now the write gate checks the events instead of the text: no note that applies to that project (its own or a global one) may still owe a verdict - each one is named - every heavy rule that applies there and has fired since the previous report must be settled in one of the three ways above - wherever it fired, because the log records when a rule fired but not in which project - and every open point from an earlier report must be closed, or carried forward exactly once. The refusal names what is missing, item by item, and sends the writer to the work itself, never to a pass that relabels in bulk. Moving a report that was filed for another project onto this one is a filing too, held to the same conditions.
- **An open point is its own note now, and the session is handed the list instead of having to go looking.** Open points used to live as prose inside a report, and a report is never injected into any session, so a session starting with fresh context was held by the block, told to do the review, and given no list at all - it could only drop silently what it had never seen. Each open point is now a small note of its own, carrying the report it came from, named in full in the block that holds the turn and summarised at session start. Closing one is a retraction with a reason; carrying it forward is allowed exactly once and covers the one filing that follows, a second carry is refused to a program and needs the owner, and the tag cannot be revised away.
- **One maintenance pass labels a store that predates all of this.** `backfill_teeth` walks every note, tries each one's teeth with the same code the write path uses, and records the honest outcome. A label records what trying found; it settles nothing on its own. `backfill_teeth --db <path to your store>` reports what it would label and, before anything is written, which of those writes the gate would refuse and why; it changes nothing unless you pass `--apply`, it is safe to run again, it never invents a proven guard, and without `--root` it skips a file check it cannot try rather than labelling it.
- **A hard guard refuses only for rules that apply where you are working.** The three guards that read only the text of a call - a required answer, a forbidden fragment in a command, a forbidden text in any file - read every rule in the store, whatever project it belonged to, so a rule written for one repository refused an ordinary call in another. They now keep only the rules of the session's own project and the global ones. A refusal for a missing required answer is now recorded like the others.
- **Weakening a heavy rule needs a reason even when it has no check.** Lowering or clearing the severity of a rule marked irreversible or costly, or removing one of its bindings, now asks for `because`, the same as weakening a checked rule. Retracting such a rule takes a reason about that rule: name what it is about, or quote what replaced it.
- **A verdict needs something to judge.** `mark` refuses an item that has never been served anywhere: there is no place it fired to judge.
- **A measurement run really leaves no trace now.** `hook --no-record` skipped the delivery events and nothing else, so it still wrote the evaluation accrual, the session watermark, the capture flag and the guard markers beside the store, and a refusal still landed in the log. It now opens the store read-only and writes no file beside it: the store's directory is byte-identical after the call. A store nobody has open is read straight from its file, so not even SQLite's own companion files appear.
- **An agent's answer the owner reads himself gets his reading rules.** A `Stop` payload that carries `agent_id` skips every answer-guard rule marked `owner_reading_only`, because an agent's answer is normally read by the session that spawned it. A program that drives a local model sends `agent_id` so its calls never count toward an assistant session's upkeep, yet the owner reads those answers directly. It can now add `"owner_reads_answer": true` to its `Stop` payload: the reading rules apply to that answer, and every upkeep question stays out of it.
- **A cited line has to exist to count as evidence.** The answer guard's evidence rule accepted anything shaped like `name.ext:NN`, so an answer could claim a check, type a file and line nobody opened, and pass. When the `Stop` payload names the session's working directory, a citation now counts only when that file exists under it and has that line; one that does not check out counts for nothing, not even through a literal escape inside it, and the reason names it. Without a working directory a citation is judged by its shape, as before.
- **One evaluation settles a batch of heavy rules, not the whole backlog.** Filing an evaluation report demanded every heavy rule that fired since the previous report and still had no real tooth or reason - on a real store, about 80 for one project, a wall that invites exactly the dodging the gate is there to stop. A report is now held to a batch of at most eight, the rules written longest ago first. The batch holds still while the evaluation works through it, a rule settled before the previous report never takes a place in it, and what the batch leaves out stays owed and leads the next report's batch. The ask for the evaluation names the batch, the refusal counts what is left, and `doctor` names both on a new `evaluation batch` line.
- **A rule about the assistant's own claims no longer fires on what it reports someone else said.** The rule that says "verify before claiming you cannot" held an answer that only reported another model's words ("the model said it had no access"). A rule marked `own_claims_only` now counts a trigger only in the assistant's own voice: not in words a reporting verb hands to another party, and not in a quote, a blockquote or a code block, unless a first-person word frames it. A real "I cannot", in Dutch or English, is still held, also right next to a report.
- **A commit, a line number and a file name with a colon count as evidence only when they are real.** After citations were looked up, the evidence rule still passed an unchecked claim on the literal words `commit`, `line` and `regel` (even inside "pipeline"), on any typed hash, and on a bare `name.rs:`. With a working directory in the `Stop` payload, a hash now counts only when that directory's git repository has the commit (judged by its shape as before where no repository answers), a line number only when a file named next to it has that line, and `.rs:` only inside a citation that checked out. The block reason names what did not count.
- **A `requires` trigger can sit inside the command it is bound to.** Its trigger had to name one of the rule's own bindings, so "a dev compose run over ssh must name the dev compose file" could not be written: the call that runs is `ssh`, and only a literal deep inside it marks the dev stack. A trigger that names no binding is now read as a literal inside the bound command: the rule stays bound to `ssh` and asks for its answer only from a call that carries the literal as whole words, leaving every other `ssh` call alone. The write gate refuses such a trigger when it is one plain word or under four characters, and the teeth test tries it inside its binding, with and without the answer, and checks that the bare binding still passes.
- **A search in a file or folder brings up what is anchored there.** Grep and Glob name their place in `path`, and the hook only ever read `file_path`, so no search fired a single file or folder rule. A search that names a path now informs about the rules anchored at that file or folder (and the folders it sits in), never those of the files under a searched folder, and it is never refused.
- **The evaluation routine says where its batch comes from and what settles one.** Its teeth step now tells a fresh assistant that the batch is not its pick but the `batch:` lines under the health check's `evaluation batch`, that the gate refuses the report until each is settled, and that only a check that bit reality, a wired check carried by an open point, or a real no-literal reason settles one - never a label the tool wrote.
- **An evaluation is held to the list it started with, and only to what fired in its own session.** The filing gate used to compute the judgement debt live and store-wide at every attempt, so the evaluation's own writes (which fire every rule bound to the `remember` moment) and parallel sessions kept adding to it: measured in a fresh evaluation, eight attempts were refused on a list of 14, 6, 13, 4, 4, 1, 5 and 4 items, and the session ended up marking sixty items useful, some it never saw fire. The list is now fixed when the evaluation starts - when the routine is opened, when the Stop hook asks for it, or at the first filing attempt - and holds only what fired in the evaluating session by then. The hook, which knows the session, hands that over to the tool server in a small file beside the store; the note that starts the evaluation names the list. Items that fired only elsewhere stay owed store-wide and `doctor` keeps naming them. An item that cannot be judged honestly can be skipped with a tag `not-judgeable:<id>:<reason>` on the report, so "when in doubt, skip" no longer collides with a debt that must reach zero.
- **A check that holds only in a worktree is refused, and doctor reads the main checkout.** A session in a worktree attached a `contains` check to code that existed only there; stored without complaint, it blocked every commit on main for eleven minutes. `remember` and `revise`, started in a worktree, now refuse a check that holds there and not in the main checkout. `doctor`, standing in a worktree or finding one under its checkouts root, judges every check against the main checkout instead - it used to take a scratch folder of worktrees as the root, called a true fact false against a lagging worktree, and a session revised the fact backwards.
- **A no-literal reason counts only after a check was tried.** Two reasons that passed both the shape and the content rule were still wrong - one said outright that the syntax was never found - and neither rule had ever carried a check. A reason now settles a heavy rule, for the filing gate, the Stop hook's teeth question and `doctor`'s teeth line alike, only when the rule's own history on the log shows a check attached at some point.
- **A change of directory no longer silences a debt.** A session that worked in a project and then moved to a folder that belongs to no project is still held to that project's debts, and its work there still counts.
- **A check that really bit counts at filing, and the gate says what an open point is.** A fresh evaluation provoked three real refusals and the report gate still named all three rules as never having met a real call, because the label is only rewritten when the rule is. The gate now reads the log: a refusal by the real hook under the check a rule carries now settles it by itself. Its refusal also spells out an open point - a separate small Report with kind, project, tag `open-point`, an id and a sentence naming the rule's id - and the write gate refuses an `open:<id>` tag on the rule itself, which looked like one and counted for nothing. An open point now carries any rule that hangs a check, including one whose file anchor is full; a rule with no check still owes a try.
- **A try never hangs live, and a reason never stands beside a check that refuses.** `revise` with `trial_check` tries the check given in the same call through the write-time proof, records the check and the result in the rule's history, and never stores it - so a no-literal reason earns its try without a check hanging on the real store that is already known to be wrong. A tried check that works is refused as a trial. A reason that nothing can catch the mistake no longer settles a rule whose own check can refuse, and the write gate refuses introducing the two together.
- **A `requires` trigger inside a URL or a path is seen where it really sits.** "/health" never matched `curl http://host:3002/health` because the character before it is a digit, while the write-time proof appended the trigger as a word of its own and reported the rule wired. A path separator now counts as a boundary, the proof tries the binding as it is when the binding already carries the trigger, and the live guard and the proof share one matcher.
- **A rule that answered the older teeth question stays correctable.** 2.4.1 began asking heavy rules anchored to a command for a sharper answer than the general one, but shipped with no allowance for rules already holding the general answer - which left those rules impossible to revise at all, including by the maintenance pass meant to label them. A rule that already carried the older answer under that exact shape may now be revised as before. Writing a new rule of that shape with only the general answer is still refused, and so is an edit that creates the shape for the first time.

**Upgrading from 2.4.0**: unpack over the old programs and run `install` once from inside your repository, so it refreshes `/thor-eval` and the project record. Restart your assistant afterwards.

## 2.4.0 (2026-09-12)

- **The evaluation ships with the install.** `install` writes `/thor-eval` into your assistant's commands. Run it at the end of a session: it judges what fired, repairs what has rotted, and gives teeth to what could stop nothing.
- **The memory asks for that evaluation.** Once per session, the Stop hook holds the turn when a project owes a verdict on ten or more notes and nothing there has been judged for a day.
- **`doctor` names the debt.** The notes that owe a verdict are listed with the place they fired (all of them with `--full`), and the line says how long ago the newest verdict was.
- **A fresh install opens the project it read.** The first note filed under your repository lands without being asked to name a new collection; the refusal text no longer points to `install --project`.
- **`revise` can clear a field on purpose**: `clear_check`, `clear_severity`, `clear_project`, `clear_expires`, `clear_key`, `clear_falsifier`. An empty string never reached the server from an assistant's tool layer.
- **Pinned notes owe no verdict.** A note bound `Always` never appears in the judgement debt, and `mark` on one says so instead of writing a verdict that changes nothing.
- **`mark` notices a repeat.** The same verdict twice in one session is not counted twice; a different verdict is written and says which one counts.
- **The crowding note measures.** On a `revise` that keeps its bindings, the note says how often the item was actually shown in the last 30 days instead of guessing that it may never be shown.
- **The response guard knows who is reading.** A rule can carry `owner_reading_only`: style rules step aside for a subagent's report to the main agent, honesty rules keep applying to everyone.
- **The hint under a truncated block runs.** It prints the real path of `serve` with `--db`, so pasting it works.
- **Weakening a checked rule needs a reason.** `revise` asks for `because` when it removes or changes a check, lowers severity, drops a binding or narrows scope; the reason is kept in the note's history. A check that is the direct opposite of another check on the same file is refused.
- **Windows release builds are reproducible.**
- Six Stop-hook debts now: judgement, crowding, false proof, setup, teeth, evaluation.

**Upgrading from 2.3.x**: unpack over the old programs and run `install` once from inside your repository. It records the project, writes `/thor-eval`, and leaves your notes untouched. Restart your assistant afterwards.

## 2.3.3 (2026-09-08)

- **The library is yours to shape.** When nothing fits, your assistant asks what the new shelf should be called and opens it under that name. An entry you no longer want can be retired with a reason; nothing is ever deleted.
- **A note stays inside its own project.** A note anchored on a file path used to reach any file with that name anywhere on your machine; now it resolves against the project it belongs to.
